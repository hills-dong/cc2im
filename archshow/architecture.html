System Overview

cc2im is a monorepo bridge that connects Claude Code (Anthropic's AI coding assistant) to messaging platforms and a web interface. Users send messages via Discord threads, Lark group chats, or a Web UI, and cc2im spawns Claude Code child processes to handle each conversation with persistent per-thread sessions.

Step-by-Step Breakdown

1
Receive

Adapter receives platform event → constructs IncomingMessage with normalized fields (platform, channelId, threadId, content, attachments)

2
Route

Router maps {platform}:{channelId} → project config. Checks for /im-* management commands. Returns null if channel not registered.

3
Thread

If threadId is null, create a new thread via adapter. For Discord: creates channel thread. For Web: generates wb_project:timestamp. Sets fallback title from first 30 chars, then async generates a better title via Claude (haiku model).

4
Persist

Save user message to DB. Create/update thread record. Send initial "⏳ Thinking..." indicator to user (or "⏳ 请稍等..." if thread is busy).

5
Invoke

SessionManager queues if thread busy, waits for concurrency slot (max 5 processes), then spawns claude --print --output-format stream-json --resume {sessionId} -p {message}. Attaches image paths if present.

6
Stream

Reads stdout line by line (NDJSON). Parses StreamInitEvent (captures session_id), StreamAssistantEvent (text blocks + tool_use tracking), StreamResultEvent (final text + tokens). Calls onEvent callback for each.

7
Live Update

CLI's handleMessage accumulates bufferedText and activity log. A setInterval timer (100ms web, 3s Discord) calls editMessage to update the "Thinking..." message with current text + activity footer.

8
Format & Deliver

Formatter extracts [react:emoji] patterns, splits text by platform limit, detects referenced image paths, creates file attachments for oversized output. Final message gets "✅ done [elapsed]" footer.

Concurrency & Queue Logic

Each thread has its own FIFO queue. When invoke() is called:

  1. If queue exists for this threadKey → push to queue, await
  2. When dequeued (or no queue) → wait for active.size < maxConcurrentProcesses
  3. Call onStart() callback → spawn process
  4. On process close → shift next from queue, or delete queue

This ensures messages to the same thread are processed sequentially, while different threads run in parallel up to the concurrency limit.

Graceful Shutdown
  1. Mark active threads as pending restart in DB
  2. sessionManager.abortAll() — SIGTERM all Claude processes
  3. adapter.stop() for each adapter
  4. store.close()
  5. process.exit(0)
Pending Restart Recovery

On startup, loads pending restarts from DB, clears the table, then for each thread:

  1. Find adapter + project config
  2. Call sessionManager.invoke() with resume message
  3. On success: update thread, send response to user
  4. On failure: retry once after 3s
  5. On second failure: mark thread as done, send error message to user
AskUserQuestion Interception

When Claude Code uses the AskUserQuestion tool during a session:

  1. Stream callback detects tool_use block with name === "AskUserQuestion"
  2. Questions stored in lastAskQuestions
  3. After invoke completes, format questions and send to user
  4. Add entry to pendingAsks Map with a Promise resolve
  5. Next message from user in same thread resolves the promise
  6. Parse answer (letter combos like "AB" or full text)
  7. Re-invoke Claude with --resume + user's answer
